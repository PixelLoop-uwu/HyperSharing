# CLAUDE.md — Hypersharing backend (Go)

Бэкенд Hypersharing: imgur-подобный сервис, но для файлов любого типа. Пост состоит из упорядоченных секций (текст + файлы). Бэкенд переписывается с Python (FastAPI) на Go, поэтому старые API и схема не обязательны к совместимости.

## Ключевые решения

- Посты неизменяемы после публикации: редактирования нет (пока). Есть только создание и удаление.
- Публичного списка постов нет: пост доступен только по прямой ссылке (случайный uuid v4). Нет и `GET /users/{username}`: ник и аватар автора видны только внутри поста.
- Регистрация необязательна. Аноним может загружать и постить, но его посты удаляются по времени (TTL), а удалить пост вручную может только зарегистрированный автор.
- Загрузка файлов возможна только против драфта поста. Загрузка, публикация и отмена драфта доступны только его владельцу: залогиненному — по сессии (`user:<uuid>`), анониму — по IP (`ip:<hash>`, `/64` для IPv6). Сам uuid драфта — лишь идентификатор, а не разрешение.
- Все файлы идут через API (tus, поток в MinIO), без прямых presigned-загрузок: так проще считать квоты.
- Дедупликации файлов нет: файл принадлежит ровно одному посту.
- Сессии: непрозрачный токен в Redis с продлением TTL при каждом запросе.

## Стек

- Go, модуль `hypersharing` (go 1.27.1)
- HTTP-роутер: `chi` (tusd монтируется как обычный handler)
- PostgreSQL 18, доступ через `pgx` + `sqlc` (SQL пишется руками, Go-код генерируется)
- Миграции: `goose`, SQL-файлы в репозитории
- Redis 7: сессии, драфты, квоты, rate limiting
- MinIO (S3) через `minio-go`; загрузки через tusd (s3store)
- Пароли: argon2id (параметры в конфиге)
- Логи: `log/slog`
- Инфраструктура: `docker-compose.yml` (Postgres, Redis, MinIO + `minio-init` для бакетов), `justfile`. Dev: инфраструктура в Docker, приложение на хосте (`just dev`).
- Фронтенд (React + Vite) проксирует `/api` на бэкенд; пути ниже даны без префикса `/api`

## Структура проекта

Feature-based, а не слои по всему проекту:

```
cmd/            точки входа (api, при необходимости worker)
internal/
  config/       загрузка и валидация конфига
  draft/        общие типы и ключи Redis для драфтов (используют post и storage)
  user/         пользователи, регистрация/логин, сессии, аватары
  post/         драфты, посты, секции, файлы поста
  storage/      tus, выдача файлов по short_key, квоты
  platform/     инфраструктурные пакеты без бизнес-логики
    s3x/        обёртка над minio-go
    ...         (db, redis, http и т.д. по мере появления)
```

Правила зависимостей:
- `platform/*` ничего не знает про `user`, `post`, `storage`.
- Фичи не импортируют друг друга напрямую; общаются через небольшие интерфейсы, объявленные на стороне потребителя.
- Внутри фичи: `handler` (HTTP) → `service` (бизнес-логика) → `repository` (БД). Handler не ходит в БД, repository не знает про HTTP.

## Схема БД

Нормализованная. Требования «читать без join» нет: join и несколько запросов допустимы.

```sql
CREATE TABLE users (
  id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  username       text NOT NULL,
  email          text NOT NULL,
  password_hash  text NOT NULL,
  email_verified boolean NOT NULL DEFAULT false,
  is_admin       boolean NOT NULL DEFAULT false,
  created_at     timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX users_username_uniq ON users (lower(username));
CREATE UNIQUE INDEX users_email_uniq    ON users (lower(email));

CREATE TABLE posts (
  id         uuid PRIMARY KEY,                 -- равен id драфта
  author_id  uuid REFERENCES users(id) ON DELETE CASCADE, -- NULL = аноним
  title      text NOT NULL DEFAULT '',
  total_size bigint NOT NULL DEFAULT 0,        -- денормализация, считается при публикации
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX posts_author_idx ON posts (author_id, created_at DESC);
CREATE INDEX posts_anon_created_idx ON posts (created_at) WHERE author_id IS NULL;

CREATE TABLE sections (
  id       uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  post_id  uuid NOT NULL REFERENCES posts(id) ON DELETE CASCADE,
  position int  NOT NULL,
  body     text NOT NULL DEFAULT '',
  UNIQUE (id, post_id),
  UNIQUE (post_id, position) DEFERRABLE INITIALLY DEFERRED
);

CREATE TABLE files (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  post_id     uuid NOT NULL,
  section_id  uuid NOT NULL,
  position    int  NOT NULL,
  name        text NOT NULL,            -- оригинальное имя, только для отображения
  mime_type   text NOT NULL,
  size        bigint NOT NULL,
  hash        text,                     -- sha256 hex, необязателен, в v1 не проверяется
  storage_key text NOT NULL,            -- ключ объекта в MinIO
  short_key   text NOT NULL UNIQUE,     -- ~6 символов в публичном URL
  created_at  timestamptz NOT NULL DEFAULT now(),
  FOREIGN KEY (section_id, post_id) REFERENCES sections(id, post_id) ON DELETE CASCADE,
  UNIQUE (section_id, position) DEFERRABLE INITIALLY DEFERRED
);
CREATE INDEX files_post_idx ON files (post_id);
```

Заметки:
- Срок жизни анонимного поста не хранится, а вычисляется: `author_id IS NULL AND created_at < now() - TTL`. Чтение поста обязано проверять тот же срок (просроченный пост даёт 404 даже до очистки).
- Из-за этого `ON DELETE SET NULL` на `author_id` нельзя: удалённый пользователь превратил бы свои посты в анонимные, и они сразу попали бы под удаление. Остаётся `CASCADE`.
- Составной FK `(section_id, post_id)` гарантирует, что файл не ссылается на секцию чужого поста.
- Порядок хранится целым `position`. Строки в БД создаются при публикации; до неё слоты живут в драфте в Redis.
- Объекты в MinIO удаляет отдельный фоновый процесс: транзакция БД до S3 не дотягивается.
- Сессий и аватаров в таблицах нет: сессии в Redis, аватар лежит в отдельном S3-бакете под ключом-uuid пользователя.

## API

Аутентификация:
- `POST /auth/register`, `POST /auth/login`, `POST /auth/logout`
- `GET /auth/me`: `id`, `email`, `username`, `created_at`

Профиль:
- `PUT /me/avatar`, `GET /me/avatar`
- `GET /me/posts`: свои посты (курсорная пагинация, только залогиненные)

Посты и загрузка:
- `POST /drafts`: создать драфт (структура поста + заявленные файлы); auth опционален. В ответе id драфта и id слотов файлов.
- `DELETE /drafts/{id}`: отменить драфт, удалить tus-загрузки, вернуть резерв квоты. Только владелец.
- `POST /drafts/{id}/publish`: опубликовать пост. Только владелец.
- `*  /uploads/`: tus (tusd handler).
- `GET /posts/{id}`: пост (секции и файлы со ссылками по `short_key`); 404 для просроченных.
- `DELETE /posts/{id}`: только автор по сессии.
- `GET /f/{short_key}`: скачивание файла с поддержкой Range.

Общее: единый JSON-формат ошибок с кодом и сообщением, префикс версии (`/api/v1`) на уровне прокси или роутера.

## Сессии и аутентификация

- Токен: `crypto/rand`, 32 байта, base64url. В Redis хранится не токен, а его SHA-256: `session:<sha256(token)>` → `user_id`, `created_at`.
- Продление при каждом запросе одним атомарным вызовом `GETEX key EX <ttl>`.
- Абсолютный максимум жизни сессии по `created_at` (например, 30 дней), иначе при sliding TTL активная сессия живёт вечно.
- Для «выйти везде» и сброса при смене пароля: множество `user_sessions:<user_id>`.
- Передача: cookie `HttpOnly`, `Secure`, `SameSite=Lax`; на изменяющих запросах проверка `Origin`.
- Два middleware: «auth обязателен» и «auth опционален» (кладёт пользователя в контекст, иначе аноним).
- Hooks tusd видят те же cookie в заголовках, проверка сессии переиспользует тот же сервис.
- Подтверждение email отложено. Заложены поле `email_verified` и интерфейс `Mailer` (объявляется в `internal/user`, реализация в `platform/mailer`). Когда понадобится: одноразовый токен (SHA-256 в Redis, TTL 24 часа), подтверждение через `POST`, отправка через сторонний сервис транзакционной почты с SPF/DKIM/DMARC, асинхронно.

## Загрузки и драфты

Драфт в Redis:
- `draft:{id}` (hash): `owner` (user_id или хеш IP; для IPv6 префикс /64), `total_size`, `structure` (JSON: заголовок, секции, порядок; после создания не меняется). TTL 12 часов, продлевается по ходу загрузки (post-receive hook), жёсткий максимум 24 часа.
- `draft:{id}:files` (hash): `file_id` → JSON `{name, mime, size, section, position, status, upload_id, storage_key}`. Каждый слот обновляется отдельным `HSET`.
- Статусы слота: `pending → uploading → done`. Переход в `uploading` атомарный (Lua), чтобы в слот не загрузили дважды. Прерванная или удалённая tus-загрузка возвращает слот в `pending`.
- Квота: `quota:{owner}:{yyyymmdd}` увеличивается атомарно при создании драфта. Брошенный драфт резерв не возвращает (проще и безопаснее), только `DELETE /drafts/{id}` возвращает. Счётчик живёт чуть больше суток.
- Активные драфты: `drafts:{owner}` как ZSET, score = время истечения, устаревшие записи чистятся при проверке лимита.

Pre-create hook tusd проверяет: драфт жив, владелец совпадает (сессия или IP — tus смонтирован через `OptionalAuth`), слот `pending`, `Upload-Length` равен заявленному размеру, `Upload-Defer-Length` запрещён, квоты не превышены.

tus-контракт (реализован в `internal/storage`): клиент передаёт `Upload-Metadata: draftId <uuid>, fileId <uuid>`. tus upload id = fileId, поэтому ключ объекта в MinIO детерминирован: `storage_key = files/{fileId}` (ObjectPrefix `files/`, служебные `.info`/`.part` в `tusmeta/`). Статусы слота: `pending → uploading → done`; `DELETE /uploads/{id}` возвращает `uploading → pending`.

Публикация:
1. короткий `SET NX` с TTL (защита от двойного клика);
2. проверка, что все слоты `done`;
3. транзакция в Postgres;
4. удаление ключей драфта.

`post.id = draft.id`: повторный publish после сбоя упирается в первичный ключ и возвращает тот же результат.

Целостность: размер сверяется на старте. Хеш целого файла в v1 не проверяется (это потребовало бы заново читать объект из MinIO); целостность передачи по возможности обеспечивается tus checksum extension (проверить поддержку в версии tusd).

## Лимиты

Стартовые значения, все в конфиге, не в коде.

| | аноним | залогиненный |
|---|---|---|
| размер поста | 100 МБ | 700 МБ |
| файлов в посте | 8 | 24 |
| секций в посте | 16 | 64 |
| срок жизни поста | 7 дней | бессрочно |
| активных драфтов | 2 на IP | 3 на пользователя |
| загрузка за сутки | 500 МБ на IP | 5 ГБ на пользователя |

Размер одного файла равен лимиту поста. Заголовок до 120 символов, текст секции до 10 000. Общая квота хранилища залогиненного пользователя: 10 ГБ (считается `SUM(size)` по `files`).

## Защита от злоупотреблений

- Главная защита объёма: TTL анонимных постов и глобальный предохранитель (если бакет заполнен больше X%, анонимные загрузки отключаются).
- Rate limiting в Redis (скользящее окно или token bucket): создание драфтов, регистрация, логин, 404 на `/f/{short_key}` (против перебора коротких ключей). IP брать только из доверенного прокси-заголовка.
- HTTP-таймауты сервера (`ReadHeaderTimeout` и др.) и `MaxBytesReader` на JSON-эндпоинтах.
- Раздача файлов: `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`; в идеале отдельный домен, чтобы файл не имел доступа к cookie основного сайта.
- Регистрация: rate limit, позже подтверждение email и, при необходимости, капча (Turnstile).

## Правила кода

Стиль:
- Отступ в проекте: 2 пробела. `gofmt` по умолчанию ставит табы, формат нужно настроить отдельно и применять единообразно.
- Имена короткие и по делу, пакеты в нижнем регистре без подчёркиваний; не называй пакеты `utils`, `common`, `helpers`.
- Экспортируй только то, что реально нужно снаружи пакета.

Архитектура:
- Интерфейсы объявляются на стороне потребителя и остаются маленькими. Не создавай интерфейс «на будущее».
- Зависимости передаются явно через конструкторы, без глобального состояния и `init()` с побочными эффектами.
- Бизнес-логика живёт в `service`, не в хендлерах и не в SQL-слое.
- Конфиг читается один раз при старте и передаётся вниз; никаких `os.Getenv` в глубине кода.

Ошибки:
- Всегда оборачивай: `fmt.Errorf("create post: %w", err)`. Проверяй через `errors.Is` / `errors.As`.
- Доменные ошибки (`ErrNotFound`, `ErrQuotaExceeded` и т.п.) объявляй в фиче; в HTTP-статус их переводит только handler.
- Не игнорируй ошибки молча и не логируй и возвращай одну и ту же ошибку одновременно: логирует верхний уровень.
- `panic` только для ошибок программиста при старте.

Контекст и конкурентность:
- `context.Context` первым аргументом в каждой функции, которая ходит в БД, Redis, S3 или сеть. Не храни контекст в структурах.
- Любая горутина имеет понятное завершение (контекст или канал остановки). Graceful shutdown обязателен.

БД и данные:
- Схема меняется только миграциями.
- Запросы параметризованные; SQL живёт в `.sql`-файлах для `sqlc`.
- Транзакция открывается в `service`, а `repository` принимает общий интерфейс запросов (db или tx).
- Всё, что приходит от клиента (размер, имя файла, структура поста), валидируется на границе.

Логирование и тесты:
- Структурные логи через `log/slog`, без `fmt.Println`. Не логируй токены, пароли и содержимое файлов.
- Юнит-тесты для сервисов и чистой логики (табличные). Интеграционные для репозиториев и S3 на реальных Postgres/MinIO из docker-compose.
- Нетривиальная логика без тестов не принимается.
